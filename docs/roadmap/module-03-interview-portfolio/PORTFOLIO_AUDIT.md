# Portfolio audit

This is a local working-tree review. Git reports existing modified and untracked paths, so a local artifact is not proof it is in the public repository. The origin name was inspected locally. Hosted CI history, remote contents, cloud resources and Desktop rendering were outside this review.

| Area | Evidence and finding | Priority before sharing |
|---|---|---|
| README and architecture | The tracked [README](../../../README.md) and [editable diagram](../../architecture/analytics-platform.mmd) explain the core flows and distinguish DAG scheduling from data flow. The README describes a seven-page Olist report. The local portfolio now has an eighth exploratory commerce page, and the newer commerce docs are local additions. | **High.** Describe tracked and local scope separately until reviewed additions land. Update page counts and architecture when promoting commerce evidence. |
| Repository organization | Code is grouped by ingestion, modeling, orchestration, analysis and reporting. The local status contains many prior changes. Some newer evidence, including the commerce warehouse guide and dashboard checks, is outside the tracked tree. | **High.** Review exact intended changes and dependencies before preparing a shareable commit. |
| Reproducibility | The Olist source CSVs are external inputs, Airflow is a separate local installation, and cloud dbt or Power BI refresh requires access. The [forecast snapshot](../../forecasting/source-snapshot.csv) and [synthetic case](../../../experimentation/CASE_STUDY.md) provide offline entry points. The case documents that its environment is incompletely locked. | **High.** Record one clean-checkout, credential-free rehearsal with version and input provenance. Keep optional cloud workflows separate. |
| Tests and CI/CD | [CI](../../../.github/workflows/ci.yml) defines pytest, credential-free dbt parse and historical GA4 isolation. It is evidence of CI configuration. There is no deployment job in this workflow. Local commerce browser and Node checks are not explicitly invoked by these workflow steps. | **High.** Link passing run evidence to a commit before claiming CI passed. Document what is tested offline and what needs vendor or warehouse access. |
| Dashboard documentation and demos | Olist has a four-page PDF and preview images. Historical GA4 has a three-page PDF and a setup guide. The assets predate the current local formatting work. The latest all-page Desktop review was not established. | **High.** Capture dated renders of the current pages and one short interaction walkthrough before calling the redesign verified. |
| Credentials and security | Ignore rules cover local environment and data files. The [Airflow guide](../../../orchestration/airflow/README.md) uses an inherited environment variable for Gemini. A limited filename and private-key/API-key pattern screen found no matches in the inspected scope. This is not a Git-history scan or a review of all local files. | **High.** Run a proper staged-file and history secret scan before making a repo public. Confirm dataset licensing and keep raw exports, traces and credentials outside the shareable evidence bundle. |
| Implemented, simulated and pending | [Experimentation](../../../experimentation/CASE_STUDY.md) is synthetic with hypothetical economics. [Forecasting](../../forecasting/README.md) is retrospective and has point-in-time limitations. [Commerce warehouse notes](../../commerce/GA4_WAREHOUSE.md) distinguish exploratory GA4 data from the offline benchmark and PostHog population. Local commerce progress records separate receipt and manual import. Those notes are historical and should be aligned with latest dated evidence before sharing. | **High.** Label each demo with source, date and evidence state. Keep offline checks, browser behavior, vendor receipt and reconciliation separate. Avoid claiming operational reliability or production deployment. |

A shareable portfolio should make three things easy to locate. Show a runnable offline example, a dated dashboard demo, and one decision memo that explains the main limitation. The audit identifies these evidence tasks. It does not revise the existing README, dashboards or models.
